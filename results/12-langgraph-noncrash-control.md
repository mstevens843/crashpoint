`handoff/langgraph-noncrash-control/CODEX-CLOSEOUT-RESPONSE.md`.

recovery measurement: the worker below is never killed.

## Question

Can normal completion be connected to prior caller-owned admission, the correct LangGraph thread, and
one independently observed effect, without deriving effect truth from runtime success?

## Experiment

One fresh identity (`lgnc-<uuid4 hex>`) is generated and used, unchanged, as the admission_id,
LangGraph thread_id, and the out-of-process ledger's intent_id. A caller-owned admission record
(reusing `langgraph_admission.initialize_admission_ledger`/`accept_run`/`read_admission` unmodified,
with a fresh identity rather than that module's fixed `"accepted-run"` thread) commits the run's
identity and original input to a SQLite row before any LangGraph call. The admission database itself
stores identity, input, and an append-only event log (`accepted` -> `completed`) - it has no timestamp
column. The UTC timestamp is generated by the harness process in memory, immediately before that
commit, and recorded only in the receipt (`admission.accepted_at_utc`); it is not separately durable
evidence the admission database itself carries, and this control does not implement or claim a
separate durable timestamping mechanism. A pre-declared contract (one invoke, no crash, one intended
effect, fresh-process observation) is written and hashed before execution and never edited afterward.

A real separate worker process (`langgraph_control.py --worker`) reads its invoke input back from that
admission row - not from its own arguments - builds an ordinary `START -> node -> END` graph with the
installed `SqliteSaver`, and calls `app.invoke(input, config, durability="sync")` exactly once. No
crash is injected. The node makes one `execute()` call to crashpoint's out-of-process ledger with
`key=None` - deliberately no retry loop, idempotency guard, or reconciliation that could hide a
duplicate crossing in a positive control.

After the worker exits, the ledger is sealed and its daemon subprocess is stopped. A newly spawned,
separate observer process (`langgraph_control_observer.py`, which never imports LangGraph) then opens
the ledger's on-disk JSONL store with its own fresh file handle - never `ledger.dump()`, the worker's
output, or a count the harness computed itself - hashes the raw bytes, verifies the record chain, and
derives the effect count/digest/reference for this run's intent_id directly from what it read. It
archives an exact copy of those bytes into the retained bundle and re-hashes the copy to confirm it
agrees with the original before the ephemeral socket/store directory is cleaned up.

A missing store is reported `STORE_MISSING` (null count); a store that reads fine but never mentions
this intent is a real, valid zero observation, reported `OBSERVED` with `effect_count=0` - the two are
never conflated (`ledger_readback.py`). The native receipt (`langgraph_control_receipt.py`) keeps
admission evidence, runtime completion, observer validity, and effect truth as separate fields, and
classifies the result as one of `EXACTLY_ONCE / DUPLICATED / DIVERGED / LOST / VOID / UNVERIFIED` from
those fields directly - not by calling `ledger.oracle.classify`, whose path-based chain check treats a
missing ledger file as a valid empty chain, which is exactly the conflation this control avoids. A
descriptive `sable_facing_mapping` on the receipt states how that classification would read under
external PASS/FAIL/UNKNOWN vocabulary without altering or gating on it.

`langgraph_control_verify.py` checks a bundle directory offline: it never imports LangGraph (verified
statically in `tests/test_langgraph_control_verify.py::test_verifier_closure_never_imports_langgraph`,
which walks the AST of its whole local-import closure) and never launches the runtime. It recomputes
the outer receipt hash, recomputes every declared artifact's SHA-256 from bytes actually in the
bundle, independently re-parses the retained ledger bytes to recompute the effect count/digests/
references (not just re-verify a hash over an untrusted summary), independently re-queries the
retained checkpoint and admission SQLite files with plain `sqlite3`, and recomputes the oracle
classification and agreement from those independently-derived facts. Every path it opens is resolved
as bundle-relative, so a relocated copy of the bundle verifies identically with no access to the
original absolute paths.

Command:

```bash
uv run --extra langgraph python -m crashpoint.harness.langgraph_control \
  --output evidence/langgraph_noncrash_control_v4 --name langgraph_noncrash_control_v4
uv run python -m crashpoint.harness.langgraph_control_verify evidence/langgraph_noncrash_control_v4
```

Focused regression tests (`tests/test_ledger_readback.py`, `tests/test_langgraph_control_receipt.py`,
`tests/test_langgraph_control.py`, `tests/test_langgraph_control_verify.py`; 108 tests) additionally
run a handful of small real non-crash executions - never a crash, never a benchmark-sized campaign -
to check: admission identity is bound before invoke and distinct across runs; existing output
directories are refused before any side effect; no owned process remains after a run; a worker timeout
still retains partial evidence and cannot PASS; an observer subprocess timeout still yields an honest
`VOID` receipt with a clearly-labeled parent-process fallback archive of the ledger bytes; an observer
internal exception (a blocked archive path) produces an `OBSERVER_ERROR` report and exit 2, never a
traceback; a checkpoint database that exists but was never fully set up is reported with an explained
null count, never crashes checkpoint counting; the required executing-source hashes are recorded
unconditionally, even when git status is simulated clean; and, against real bundles (moved, copied,
and selectively mutated one field at a time, with outer hashes recomputed after every mutation), that
missing/malformed observer reports, missing source modules, `accepted_before_invoke=False`,
`worker_exit_status` disagreeing with `worker_ok`, `invoke_count` disagreeing with the contract, a
retained `contract.json` disagreeing with the receipt's embedded expectation, missing readback,
corrupt bytes, a broken chain, wrong identity, an altered count or effect reference, a missing
required-but-nullable field, malformed JSON/types, and invalid UTF-8 are all rejected for their own
specific reason (never a bare traceback, via both the Python API and the CLI), while a constructed
valid-zero and a constructed valid-duplicate ledger correctly fail the *positive control*
(`LOST` / `DUPLICATED`) without ever being reported as a missing observation. A dynamic subprocess
test poisons `sys.modules['langgraph'] = None` before invoking the verifier, proving no future import
path can reach LangGraph, not just the modules a static AST scan happens to list.

A second review found and fixed three further gaps, each with its own production-path (not
parser-only) regression test. A real worker and a real observer both execute, and the observer
subprocess's own report file is overwritten only after it completes, before `run_primary_control()`
reads it back; the harness must not crash and must still retain a receipt, the original bad report
byte-for-byte, and the worker's genuine ledger effect (via the observer's own archive or, when the
observer never got that far, the labeled parent fallback) for each of `[]`, `null`, `{}`, and
invalid JSON. A companion test neutralizes just the new shape-validation step and confirms the exact
same scenario then crashes with `AttributeError` - proving the validation step is what prevents it,
not an unrelated change. Three bundle-confinement tests point a declared path at a real, correctly
hashed file outside the bundle - an absolute path, a `..`-escaping relative path, and a symlink
inside the bundle pointing outside it (both for `contract.path` and for a `source/` module copy) -
and all four are rejected before any hash comparison; a fifth confirms an honest, unmodified
relocated bundle still verifies clean. One test reproduces `observer.exit_status=2` alongside an
otherwise byte-verified `OBSERVED` report and confirms it cannot verify as passed while the genuine
readback evidence (`observer.status`, `effect.observed_count`) stays intact and reported. All four
path-confinement tests, and the compute_agreement-level observer-exit-status test, were confirmed to
fail against a temporarily reverted copy of the fix (restored immediately afterward, diffed byte-for-
byte against a backup to confirm the restore) before being confirmed to pass with it - the assignment's
requested red/green proof, not just a description of the fix.

## Claim boundary

This is a positive control and an evidence-portability test, not a LangGraph fix, not a crash or
recovery measurement, not a global exactly-once guarantee, not provider idempotency, not
admission/dispatch fencing, and not SABLE certification. It is one recorded run (n=1 by design): no
statistical rate or Wilson interval is claimed. Offline verification establishes that the retained
evidence is internally consistent and supports what the receipt claims - not an independent rerun or
an authenticated real-world effect, and a checksum agreeing with itself does not by itself prove the
effect happened. The observer's process ID is retained as diagnostic metadata only; it is not
cryptographic proof of isolation, and both the worker and the observer run as the same OS user with no
additional sandboxing. The external effect is a harmless local ledger fixture, not a real provider.

Not every claim in the receipt carries the same kind of check, and the verifier does not report which
kind backs a given PASS - a reader has to know the difference. Genuinely **re-derived from raw bytes,
independent of any self-report**: the ledger effect count/digests/references (reparsed from the
archived JSONL and its hash chain), the thread-scoped checkpoint count (requeried from the retained
SQLite file), and the admission identity/input/event sequence (requeried from the retained admission
SQLite file). Only **checksum-consistency, not independent proof of truth**: installed package
versions, the Python/platform strings, `accepted_at_utc` and other recorded timestamps, process IDs,
and the outer receipt hash itself - these are recomputed and cross-checked for internal agreement
(the file has not changed since it was hashed, the declared value matches what was recorded), not
independently re-derived from a second, unrelated source the way the ledger/checkpoint/admission
facts are. A PASS means both kinds of check succeeded; it does not mean both kinds of check carry
equal evidentiary weight.

## SABLE mapping status

Mathew has already asked socksninja for a pinned submission schema and verifier command in the
`#8764` thread, and socksninja offered to handle the field mapping. No pinned schema or mapping was
available at the time of this entry, so none is integrated here: native evidence is unchanged, and the
receipt's `sable_facing_mapping` field states only a descriptive reading (`EXACTLY_ONCE` -> PASS;
`LOST`/`DUPLICATED`/`DIVERGED` -> FAIL; `VOID`/`UNVERIFIED` -> UNKNOWN; admission status reported
independently of the effect count) for whenever that mapping is defined. This is not a blocker on the
native control above.
